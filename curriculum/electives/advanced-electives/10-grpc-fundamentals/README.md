# gRPC fundamentals

## When you need this

Go services that communicate via REST/JSON face slow serialization, no built-in contract enforcement, and no streaming support. gRPC fundamentals solve this by providing a contract-first RPC framework with protobuf serialization, HTTP/2 transport, bidirectional streaming, and code generation for both server and client stubs.

## When you do not need this

When simpler concrete types or standard core library primitives suffice without adding abstraction overhead.

## Prerequisites

- elective-09

## Mental model

gRPC is a Remote Procedure Call framework where services and messages are defined in a .proto file. The protoc compiler generates server interfaces and client stubs in multiple languages. The server implements the generated interface, registers it with a gRPC server, and listens for requests. The client stub provides type-safe methods that make RPCs to the server over HTTP/2.

## How it works

gRPC uses HTTP/2 for transport, with protobuf as the default serialization format. Each RPC is an HTTP/2 stream multiplexed over a single TCP connection. The server listens on a TCP port and accepts incoming streams. Client stubs marshal request messages to protobuf, send them over HTTP/2, and unmarshal response messages. gRPC supports four RPC types: unary (request-response), server-streaming, client-streaming, and bidirectional streaming.

## Tradeoffs

- gRPC over HTTP/2 provides multiplexing: multiple RPC calls share a single TCP connection, reducing connection overhead
- Protobuf serialization is ~5-10x faster than JSON serialization for equivalent payloads
- gRPC's flow control (HTTP/2 stream-level) prevents a fast sender from overwhelming a slow receiver
- Streaming RPCs have lower per-message overhead than unary RPCs because the HTTP/2 connection and headers are reused

## Common mistakes

- Not setting up TLS — gRPC requires TLS by default; use grpc.WithTransportCredentials(insecure.NewCredentials()) for development only.
- Using blocking calls without timeouts — a gRPC call with no context deadline blocks indefinitely if the server is down.
- Ignoring deadlines and cancellation on the server — the server should check ctx.Err() between processing steps to stop work when the client cancels.
- Registering the wrong service — ServiceServer must be registered with the exact name generated by protoc-gen-go-grpc.
- Mixing gRPC status codes with HTTP status codes — gRPC uses its own status codes (codes.NotFound, codes.Internal) that are different from HTTP status codes.

## Practice task

The learner must define a .proto service with at least one unary RPC, generate Go server and client code using protoc with the gRPC plugin, implement the server, write a client that calls the RPC with a context deadline, and verify the response is correct.

## Production notes

gRPC is used in every microservice architecture for internal service-to-service communication. Google uses gRPC for all internal RPC. Kubernetes uses gRPC for the kubelet API. Envoy uses gRPC for xDS configuration. Go microservices use gRPC for high-throughput, low-latency internal APIs between services.
